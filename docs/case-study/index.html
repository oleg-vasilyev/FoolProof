The harness that learned to check itself

FoolProof is a small Telegram bot that keeps score at Durak. One person, working with Claude Code, built it in five weeks, and the bot is the least interesting part. Around it grew a set of rules, checks, skills and agents that decide how the next line of code gets written, and that set was rewritten more often than the bot was. This is the story of that set: what broke, what replaced it, and what it looks like today.

Every claim here comes from the commit history, every number is read from git, and every hash links to its commit. How that was done is told at the end.

Thirty-seven days on one strip

One bar per commit, coloured by era. A diamond above a bar is a release tag. Of the thirty-seven days, twenty-four have commits. The six eras are this page's division, not the repository's: the lines fall where the subject of the work changed. Hover or tap a bar to read the commit; click an era name to jump to its chapter.

Terms

What "the harness" means here

The harness is everything in the repository that is not the product.

  • CLAUDE.md

    The rules loaded before every session. Style, layering, testing, gates.

  • Skills

    Procedures loaded for one kind of job: writing a spec (the test file of one module), adding a feature, finishing a phase.

  • Agents

    Separate model instances with a brief and a contract: a reviewer, a designer, and cold readers, who are deliberately not told what they are looking at.

  • Hooks

    Scripts that fire on an edit or at the end of a turn, that is, of one reply from the model.

  • Lint rules and gates

    What a machine refuses, and what must be green before a commit or a tag.

  • Documents

    The spec, the debt list, the flow drawing, the logbook, and the check that holds all of them against the code.

A few more words recur in the project's own sense. The owner is the one person who sets the tasks and makes the decisions. The other side of the conversation is the model, and one of its replies is a turn. A phase is any bounded list of changes, feature or not, that ends at a commit or a tag. A gate is a check a phase must pass on the way.

One question the history keeps asking: where in the harness does a rule belong, in the text the model reads or in the toolchain, meaning the lint, the hooks and the checks a machine runs. The first answer was given on 29 July and never changed: "Prose is for judgement; anything else belongs in the toolchain." e88417a Everything that follows is the story of that answer being tested.

Era 1 of 628–29 Julycommits 1–30

Two Markdown files

The repository begins with no code. The first commit is a spec, PLAN.md, and a rulebook, CLAUDE.md, adapted from a sibling project. 44f6f66 The rulebook already says the things the project would spend a month enforcing: no comments in the source, a named constant for every number, one file allowed to contain SQL, and two more in the same spirit. The one thing it did not have was a check. How the checks would be built was settled in the first two days.

The second commit adds the first hook: at the end of every turn it runs the lint autofix. The third adds ESLint with five rules, and the comment at the top of the config admits the limit: the no-comments rule "has no ESLint equivalent and stays a review convention." That sentence lasted one day.

Tests arrive, and then a grader for the tests

On 29 July the code got 312 tests in fourteen files and a coverage gate at 70%. 9276ad7 The same day it got Stryker, a mutation-testing tool. It plants small deliberate breaks in the code; each such break is called a mutant. Then it counts how many mutants the tests noticed. The commit says why: "coverage says a line ran; it does not say a test would notice if that line broke."

The first run scored 88.4%. That was the project's first mutation score; by the end of the era it had reached 94.78%, and a chart in era 3 carries it into September. 508de4e The line below which the gate fails was raised from its initial 60 to 85 in those same days, so that the gate "bites on a regression" rather than hanging there for show.

The investment paid back at once. Mutation testing found what coverage could not: tests that passed for the wrong reason. The first example: a dependency in a test had been replaced by a stub, and the test checked only that the stub was called, not what the real dependency would have done. The second: one test passed only because the test before it had left a stub behind. Stryker stayed with the project for all five weeks.

The rules move out of prose

Commit 26, "make the checkable conventions checkable", set the shape of the harness. e88417a Three paragraphs of the rulebook became three ESLint rules written straight into the config: no comments, named numbers, blank lines after imports. The code was split into layers, shared code, game logic, rendering, Telegram handlers, and the layers became zones of banned imports: what may not import what. Each zone was proved with a deliberate violation. A hook on every edit started linting each file as it was written.

The same commit brought the first two skills and the first agent. The skill finish-phase, where the gates moved out of CLAUDE.md. The skill add-repository-method, for new queries to the database. And the agent phase-reviewer, which reads a whole diff and is told "Do not fix anything."

Two more ideas from the same two days survived everything that came after.

The first decides which document a fact belongs to. It was written when four subjects turned up in both PLAN.md and CLAUDE.md. The question is: would this still be true if the bot were rewritten in Python? If yes, the fact belongs in PLAN.md; if no, in CLAUDE.md. "A fact lives where its reason lives; the other document gets a pointer, never a retelling." 0afd7b2

The second is about tests: units by default, integration by exception. A spec tests one file and replaces everything else with stubs.

By the end of 29 July the testing craft had outgrown the rulebook and became the third skill, write-a-spec, and the tests stood at 418 by the end of the day. CLAUDE.md itself had nearly doubled in two days and was cut back: "CLAUDE.md is loaded on every turn, so it should hold what is true while writing any line of code." 66ff3bd It would not stay inside those bounds.

Era 2 of 630 July – 2 Augustcommits 31–66

Features you can delete, and rules that prove they fire

Era 1 made the rules checkable. Era 2 found out that a checkable rule can be dead, and that nothing tells you.

It starts by turning the source tree inside out. Instead of layers at the top (game/, render/, bot/), each feature became a folder with those layers inside it, and the rule was stated as a test: "a feature is a folder you can delete." It was verified by deleting one. 476f239 Every import came to be written from the root, through an alias with a hash sign (a name like #shared/… in place of a relative path): the alias names the folder, so an import from another feature shows in the line itself, which a path made of dots never does.

A rule found dead, four times in one day

Fencing features off from each other with lint produced the lesson the project would repeat most often. The feature-independence rule was written, enabled and green. It did not work. On 30 July four commits that day kept finding something dead, five findings in four commits: three versions of the rule itself, and two exemptions beside it.

The first two versions of the rule did nothing: first a path pattern never matched a relative import, then two config blocks set the same rule and silently replaced each other. 476f239 The third version was killed by the pattern library: it read the hash-sign aliases as comments, the pattern matched no import at all, and the zone passed everything. 40d8179

The remaining two of the four commits found exemptions dead outside the zones. The logger had moved to a folder, and the exemption that allowed it what the rest may not was left pointing at a file that no longer existed. 4d6b389 A Stryker exclusion for the database-connection file was orphaned the same way. After the file moved, Stryker began mutating it, and there is nothing to assert in it: housekeeping statements and the schema. Nine mutants no test could kill dragged the score down. f749a9c

None of these failures made a sound. The response was a habit rather than a fix: "a new zone is not finished until a deliberate violation has been shown to fail the lint." Thirteen deliberate violations were run to prove one commit.

"a rule that fires and a rule that is dead look identical from the outside." f749a9c · 30 July

A fake Telegram

By 31 July the bot could retry, restart itself and report on its own state. Then it got a rig (called e2e in the code): a fake Bot API server and scenarios that play a whole evening against the bot, one sitting at the table over several games, tap by tap. One scenario file is one evening, with several checks, or cases, inside it; where a tile at the end of an era gives an e2e number, it counts cases. 3ab3c9c The rules for the fake: it only records what it is sent, never decides anything itself, and must refuse everything the real one refuses.

The rig worked, but it was not yet a gate. Its seven known faults were written honestly into a new file, TECH-DEBT.md, along with a rule for the file itself: "an entry names a trigger, not a wish." "Split the file" is a wish; "split it when a fifth job arrives" is a trigger, the event after which the debt has to be paid. 0505b9b

The rig earned its keep seventy minutes later. A new screen with buttons was given a narrow obligation: "a feature with an inline keyboard gets scenarios"; an inline keyboard is those buttons under the bot's message. The scenarios immediately caught two wrong assumptions of the model's own about the bot's behaviour, and the model wrote that down in the commit message. aea4238 The rig becomes a gate in era 3.

The cost of a gate

The project learned what a gate costs on that same new screen. It "took an hour and most of a model budget, and the breakdown was not the feature: eight Stryker invocations where two would have done." A model budget is the amount of text the model can read and write in one session, and every gate's output spends it. The answer was a mode that mutates only the changed files: 63 seconds instead of four and a half minutes. 66564c9

Two rules came with it and stayed. First: "Never re-run a gate to re-read its output." Second: one round of survivor-killing per phase. Survivors are the mutants no test caught, and they are killed by writing the missing tests.

The rulebook overflows

CLAUDE.md had been the default place to append every lesson, and it reached 585 lines. It was cut to 354 by moving rather than deleting: the rig's rules went to its own README, the layering procedure to a new add-a-feature skill. 4a3d0a9

Twenty-three minutes later came the commit "make the documents check themselves". It observed that the documents had now been de-duplicated twice, and drew the conclusion: the rule itself was not at fault, the fault was that nobody checked it. And it added the documents gate the rest of this story calls docs:check. 29fe4d5 At first it checked links, the README tree against the real folders, the script table against package.json, and a 380-line budget on CLAUDE.md. Its first run found two undocumented scripts. By the end of the story it holds more than thirty groups of checks, each about one subject; this page calls such a group a family.

A lesson left in the chat is gone

The era ends with the retrospective, and its first attempt failed. The retrospective was hung on compaction: when a conversation stops fitting in the model's memory it is squeezed down to a short summary, and the hook was to ask five questions first, about rework, repeated commands, subagents, sequencing and re-reading. It was deleted the same day. A compaction hook cannot return a word into the conversation, so it simply failed on every compaction, and compaction was "the worst moment available" anyway. ec3d818

The retrospective became a gate, the fifth in order and, at the time, the last. It also became a skill of its own.

Its very first outputs rewrote the delegation policy. Before: "mechanical work goes to a subagent on a cheaper model." The rule was replaced by a measurement: one phase had spent 493k tokens across six agents and only the review had paid for itself. Hence a narrower rule, which the owner overrules in era 4: delegate only when your own context is scarce. ecc6395

This era learned to prove that a rule fires. The next one finds a hole in a proven rule too.

Era 3 of 65–7 Augustcommits 67–121

Scenarios become a gate, states become tables

Three days and five releases, in which the checks stopped reading only the documents and started reading the code as well. The bot also learned Russian.

The rig becomes a gate

The rig still had seven recorded problems. Six were closed in one commit. The seventh, a graceful shutdown of the bot on a signal, cannot be played on Windows, where the system does not deliver that signal to a child process.

But before they could be a gate, the scenarios had to be taught to end the way a real evening ends, not in mid-sentence. The bot's message holding the current game, with buttons under it, is called the card here. Eight of sixteen scenarios broke off mid-card, leaving it with its buttons still open, and the rig now fails any that do.

The gate plays only the scenarios the diff can reach: for a phase inside one feature that is usually two or three scenario files and about fifteen seconds. 52c0f73 From that commit the phase ends with six gates in a fixed order; the rig came in fourth, and era 2's five gates became six: lint and types, coverage, mutation over the diff, e2e over the diff, the review, the retrospective. "Over the diff" means over the files the phase changed, and no others.

Writing a scenario got its own skill, and the reason is not about scenarios but about what makes a skill open: the model opens a skill when its description matches what the model is doing right now. CLAUDE.md said: if you touch the scenario folder, read the README. A phase edited a scenario "without opening the README once, because that felt like adding a case, not like touching e2e/." The skill now surfaces on "editing a scenario file" rather than on "touching a folder." a0fcb61 The same lesson returns in era 4, and costs more.

The rule that caught its own author

Every string the code used as a name for a game phase, a button press, an outcome or a refusal was moved into a table per feature. Then a lint rule banned writing such a name as a string anywhere else. Merely installing it caught five real ones in the shared code. 3c0b283

Specs were exempt at first. Three commits later the review found a spec comparing a state against a bare string. The spec had been added after the rule existed, and the same model that wrote the rule had written it. The rule was extended to specs, and along the way it caught five more sites in the production code itself. a89a991

Then a release review found a function still returning a game state as a string, well after the state table existed. The rule knew three shapes a state can be spelled in as a string, and a value returned from a function was a fourth. Hence one more step in the ritual for proving a rule, the one from era 2: once the rule is shown to fire, search the whole tree once for the shapes it cannot reach. "A lint rule catches the syntax somebody thought of." dc2602c

docs:check learns to read the code

The documents gate grew from links and budgets into a truth-checker. It grew one family of checks at a time, and each family was added after something had been found wrong.

One family checks the database schema: the SQL in PLAN.md against the SQL the bot actually runs. It arrived after a schema recreated from the document failed the first command: the database refused a record with a required field missing. a24c0d4

Another redraws the posters, the statistics pictures the bot sends into the chat, and compares them with the committed ones: one changed colour code, and the gate is red. It arrived after the posters were compared with their own design mockup and the comparison found "three different palettes in play, two font families and two widths." No document said which was right, because no check held it. 73b4f3a

A third counts the files in a folder and fails one holding more than nine. It came in the same commit that split two overgrown folders into subfolders by subject, and the number is deliberately generous: the count only makes somebody ask whether to split. cae506a

The same evening two of the new subfolders were renamed. They had first been named after an activity, "opening" and "seating"; the new names say what the feature's commands are about: the line-up of players, and the screen a player sees. a1dc566

In those same days the bot learned Russian. A chat picks its own language, and the bot's lines became a parameter passed down the calls rather than an import, which would have pinned the bot to one language. fa668dc

Two gates found lying

The release of 1.7.0 says it plainly: "Two gates were found lying on the way, both by accident and both for as long as they have existed." 4422ddb

Both lied the same way: they were green by luck, not because they checked what they promised. The first was the rig's quiet window, the pause a scenario waits before it reads the screen. It was 600 ms. The usual poster render grew from 460 to 540 ms, the headroom shrank to 60 ms, and that stopped being enough: the picture began landing after the window had closed, and five of seventeen scenarios went red on a working bot. The failure looked exactly like flakiness, a random fail, and was measured instead of waved off: the window was doubled. 2e7c639

The second was the documents gate, which could not read a checkout, a working copy of the repository, whose files carried the Windows line endings, CRLF. A fresh clone on Windows gets exactly those, but the author's working copy happened to hold the Unix endings, so the gate was green. 6ddd56e On a fresh clone it would have gone red on a tree where nothing was wrong, reporting every table undescribed. Two unrelated things happen in the next era: the bot leaves the laptop for a server, and the first gate no machine can answer appears.

Era 4 of 611–14 Augustcommits 122–184

The bot leaves the laptop

Sixty-three commits in four days, ten releases, and the largest change of setting: the bot moved to a server. With it came the first gate no machine can answer and the first checkup of the harness itself.

The gate a machine cannot answer

A poster is a picture, and no test reads one. The gallery gate takes nine awkward evenings and draws both posters for them, the chronology and the awards. That makes seventeen pictures: one evening earned no awards, so it has no awards sheet. The gate asks whoever looks for "specific claims, not a verdict." It came in fifth, and the gates became seven. ce3c70c Its first run caught two holes in the rules by which the bot hands out awards for an evening (captions like THE COMEBACK that the poster grants players on the night's results), and a line of text leaving the card. Two days later the gate was moved to after the review, because "a picture checked at gate five could be stale by gate six." 743adaa Who should look at the picture is only settled in era 5.

"'looked, fine' is the green light with nothing behind it" ce3c70c · 11 August

Delegation becomes the rule

The rule from era 2, delegate only when your own context is scarce, was overruled by the owner. An independent scope now goes to a subagent at once when three conditions hold: the work touches no file the model itself has open, the brief fits one message, and only the result matters. The review became "always the phase-reviewer subagent, and never a re-read." 0352b2b The retrospective was told to count how many such scopes were delegated and how many were not. A new default rarely fails by being used badly. More often it is quietly not used, and without the count nobody notices.

A later commit added the reviewer's limit: it reads the diff and runs nothing, so "a green review of a shell script, a systemd unit or a workflow is half a gate." All three are files only a run can check: the unit tells the server how to start the bot, the workflow tells GitHub what to run on every push. 6a4c252

Deploy, and three wrong lock files

The server pulls the newest tag every five minutes; nothing pushes to it. cfd02a1

The move's main trouble came from the lock file, the list of exact dependency versions. Written on Windows, it failed on Linux twice in this era, and a third time a week later. Each failure left a mark. First a trial install that changes nothing on disk was added to the gate. Then came the admission that on the laptop this trial had passed both times and predicted nothing. Finally a rule was written down: a broken lock file is repaired by restoring the lines that went missing from it, not by rebuilding it from scratch. ab89f77

The single check split into three by what is at stake. Before a push: lint, types and the documents, run by CI on every push, because a push changes not the bot but the website (the project's page on GitHub Pages) and the documents. At the end of a phase: the four machine gates as one command, locally. Before a tag: the full battery, coverage, every mutant, every scenario. f58e793

The battery sits in a git hook on the developer's machine and runs before the tag leaves for GitHub. The order is forced: the server pulls a tag the moment it appears and waits for nobody. A red CI after that stops nothing; it can only report that a broken bot is already on the server. 3b22b7c

The flow gets drawn, and the drawing gets hooks

The whole development loop was drawn as a sequence diagram and given its own file, DEVELOPMENT-FLOW.md. edc1148 Today the drawing has eight stages: framing the task and the mockup, code and tests, the machine gates, a review by an agent that did not write the diff, reading the sentences and syncing the pictures, the retrospective, the release, and the checkup.

It is the owner's drawing, and two things follow. It may not be changed quietly: the owner would meet the change as a diff months later, with the reasoning gone. And permission may not be asked for either: that stalls a finished phase on a decision already delegated. So the rule is to do it and say so: move the step, then report it in the closing message, with counts rather than an impression. 5eb6933 Three things watch the drawing. A hook states that obligation the moment the file is edited. A check on the commit message refuses a commit that moves a step without saying what moved and why. And docs:check fails if the drawing names a skill or script that does not exist. 912be9b

Nothing audits the auditors

The deep-checkup agent was written to run weekly, "believe nothing on say-so," fix nothing, and return a detailed report in which every verdict cites a command and its output. 4e56b66 Its first run took 33 minutes and produced thirteen findings. The highest: no backup existed and no restore had been rehearsed. A verified daily backup followed, and the other twelve findings closed in one commit. 0ba2815

The retrospective that was skipped

One phase "ran six gates and released without the seventh"; there were seven gates by then, and the retrospective stood seventh. The first explanation blamed the release feeling like the end. The next commit corrected it at the owner's word: the phase had worked from the checkup's findings register, 27 rows, and not one row was a gate; when the register emptied, the empty list read as a finished phase, and the skill holding the gates was never opened. 6799bd8 The fix was not another rule but a change in what makes a skill open. Every skill description was checked and a third of them rewritten to name the task the skill is needed on: "a phase being wrapped up", "interfaces still being frozen". Not a retelling of what the skill is about but a condition, because "a skill description is not documentation about the skill — it is the trigger that decides whether the skill is opened at all." fdab9be And docs:check began failing when a skill or agent is named nowhere in CLAUDE.md. f6f617b Era 3 had met the same lesson on the scenarios; here it cost a skipped gate. In the next era the harness gains readers who are told nothing on purpose, and every agent a contract for what it must be told and what it must return.

Era 5 of 619–25 Augustcommits 185–244

Cold readers and the budget squeeze

The product got its third poster, after the evening's chronology and its awards: one player's whole career. 2b1353b The harness got five agents, most of them readers who are told nothing on purpose. And then a set of limits on how much harness there may be.

The author cannot read their own drawing

A released poster carried a hint line beside a chart heading: "one dot per evening — 3 more evenings". The chart was not on the poster yet: it appears once enough evenings have accumulated, and until then a hint stands in its place. This one described the coming chart, one dot per evening, three evenings short of appearing; what would arrive, it never said. The owner read it cold and asked what it meant. That is the origin of the cold readers. poster-reader is briefed with pictures and the list of lines on them, and nothing else. It reads them "cold, with no idea what any of it is for." da50714 The gallery gate became, at the time, "the one gate you may not perform yourself." The gallery had grown to nearly thirty drawings by then, and the first run with this reader reported seventeen findings.

The same failure existed in words. First, reading one real evening before shipping became a gate, owed whenever a phase changes what a poster says. Until then no gate in the project had asked what the evening's chronology actually says. 93c1456

Then two real evenings were taken, and what the bot told the players about them was read: ten minutes found eight defects. So copy-reader was born: it reads every line the bot can say, in both languages, with real values filled in, and asks whether a person would say it. That reading became one more gate, and with the two inserted gates there were nine. d45f2f0 Its first readings found some sixty things, most of which were acted on. It was then moved earlier: to the moment a table of lines is written, before anything is built on it.

The plan-reviewer agent works at the very start of a phase, when the plan exists and the code does not. It gets the owner's words and the agreed function signatures, nothing more, and comes with "You may come back with nothing": the reviewer owes no finding, only an account of what it checked. Calibrated on a plan with three planted faults, it found all three and a fourth. e64c8cd

poster-designer is the only one of the new agents that draws rather than reads. It returns two things: a contact sheet, one image with every edge case beside the neighbouring poster, and an inventory of everything written on it in a player's words.

"It is the only reader here whose ignorance is the instrument." da50714 · 20 August

A gate that silently does not apply

The career poster shipped in two releases with no gallery case, because no rule said a new poster owed one: "A gate that does not apply is indistinguishable from a gate with nothing to report." da16c8d

Next the checkers themselves were checked. A checkup broke every docs:check rule on purpose, and three stayed green.

Then the tooling itself was run through Stryker: the tests caught only 47.17% of the mutants in the document checks. The checks were rewritten as pure functions with specs and given their own Stryker run with an 80% bar; the tiles call that a second Stryker family. Separate, because an average over the whole tree would have hidden the failure: by the commit's own arithmetic, the tooling's mutants averaged with the bot's would have read as 93%. 471cac4

Budgets everywhere

CLAUDE.md had had a line budget since era 2. Now every skill got one, and so did TECH-DEBT.md. The finish-phase skill had grown to 722 lines. It was cut to 459 with five pages moved into files beside it, and the budgets were lowered in the same commit "so the split cannot be a way to turn the counter off." ab68474

An outside review of the process, run by a fresh model with no memory of the work, measured how much effort was going into the harness itself: 16% of five days' changed lines had gone into the process rather than the product. Separately it counted releases: eight in four days, almost one every half day, each one restarting the bot and paying for a full mutation run and a full run of the rig again. fff3c5f In response, three things became conditional. A tag only when a player or the operator gets something new. Delegated writing only above ten files. A retrospective only when there is something to count. The tag rule shows in the history itself: the era ends with eight consecutive commits marked "Tag: none", no tag, in their messages.

The last commit of the era tested the claim that a skill should state outcomes rather than steps. The claim did not hold. One skill was rewritten from scratch, to almost half its length, and lost six concrete instructions on what to do. They went the same way each time: the account of the breakage that had produced an instruction survived, the instruction itself did not, because an instruction reads like a step-by-step recipe, which is what the brief said to remove. The commit puts it this way: "the war stories survived as symptoms while the fixes they bought were compressed away." With that in the brief, another skill was cut without losing a single instruction. A skill-auditor agent now inventories a skill rule by rule before anyone shortens it. 784b26c

Every agent also got a contract: what its brief must carry and what it returns, and the reply has to open with a verdict line: two numbers, how much was covered and how much was found, with the findings themselves after it. The verdict does not replace the findings: it is their summary, and it shows whether the whole scope was covered. The reason: the report of an agent that checked less than it was asked to is indistinguishable from a full one, and nobody further down the chain checks it again. ba4603f

Seventeen minutes after the contracts commit came a hook on the end of a turn. One phase had stopped on a message that listed what was left, ended with "Continuing", and then did nothing. No gate could have noticed: every gate judges a diff, and there was no diff. The hook now reads the last sentence of a reply and refuses a turn that ends by announcing work instead of doing it. 2239ef0 What remained was to teach the harness to remember what it had done. That is the last era's work.

Era 6 of 626 August – 2 Septembercommits 245–274

The harness keeps records of itself

The last era added almost no new parts. Instead the harness turned on itself: where the lint was blind, how a skill learns that its turn has come, and how to keep a record of a finished phase after the chat is gone. And along the way, the numbers the harness quoted about itself turned out not to match git.

Blind spots in the lint

A round of skill audits found where the lint was blind. ESLint had never been run on the scenario folder. And the import zones read only static import statements, while over a hundred spec files loaded the code under test with await import(...). Every ban is now written twice, for static and for dynamic imports. fee84a4 Two more rules moved from prose into lint. One is as old as the first commit: only one file may open the database. 76a0ee0 The other: every screen's Cancel and Confirm row is assembled in one place. 6232fe5 And the hand-written list of features in the lint config was replaced by reading the folder, because "a folder left off it got no fence at all, silently." 01ef471

Where a skill says when it is due

CLAUDE.md had opened with a routing table since era 2: what you are doing, and which skill to read for it. The skill's own description played the same role, and nobody checked either: era 4 had taught the descriptions to name the task, but not one named the stage of the flow, and the table and the descriptions had drifted apart. The table was deleted as a second copy of a fact already held in the descriptions. Each skill's description now names its stage itself, and docs:check keeps the description, the skill's title and the flow drawing in agreement with one another. When the gate was wired in it fired on every skill: not one description in the repository said when it was due. Since then the drawing keeps count of the skills: it draws every skill and every agent at its stage, and docs:check checks it in both directions. 01ef471 The description of finish-phase flipped from "Load it when ANY list of changes to this repository is accepted" to "Do NOT load it at stage 1," after the checkup found that wording firing two stages early.

The flow, corrected five times in a day

The flow drawing was read as prose, step by step, and several steps turned out not to sit where they happen. Two steps every phase needs, studying the project and reading the debt list, sat in the branch only a bug fix enters. Another example is a question that can be settled by opening files in the repository; such a question goes to a separate agent. The drawing had that step at stage 4, beside the review. In fact it happens at stage 1, before the owner is asked anything: the repository is asked before the owner. 8a1bfc2 On 26 August five commits in a row corrected where steps sit on the drawing (two more that day drew in the steps about the phase log), and two of the five admitted that "nothing mechanical checks that a step sits where it actually happens." 650cdec 3beac4c

The logbook

The answer to that was a record. The logbook folder holds one log per phase, written at the retrospective: what was asked, what kind of work it was, what ran, what was delegated, what was rebuilt, and which gate found each defect. db81a3a Two fields of a log, the path taken and the stages skipped, name the stages in the drawing's own words, and between them they must list every stage without exception. So a phase that quietly went round a stage reads differently from one that did not mention it. f4b09e7

The one rule that matters: "A number you did not measure is written not measured, never estimated." The first log written under it showed why. It had two counts wrong: both figures could have been checked with one git log command, and both erred in the flattering direction, the one that made the day read better. db81a3a

The folder beside it keeps every checkup report, and none is ever pruned. Each carries a measurements table, so the next visit can ask whether a number moved. The first report in it is from a new run at the end of August, not the one era 4 describes: 6823 mutants, 121 survived; 178 e2e cases in 109 seconds on a cold clone, a freshly downloaded copy of the repository with no caches; 1.7 GB of leftover reports. b8cb5ea

Counts rot

The most repeated lesson of the last era is small. "129 spec files with dynamic imports" was 102, because a grep counted too much. A line-count column in TECH-DEBT.md was dropped because half of it was stale and no gate could have said so. The number of awards the bot can hand out for an evening was "thirty-six" in six places, and it was forty-five. Then the number was removed entirely, with a gate for it considered and rejected: "a check defends a fact something depends on, and nothing depends on this one." 25108af The patterns collected below were made not from these small lessons but from the failures of all six eras. The last era only taught the harness not to forget them.

What kept coming back

Six patterns run through the whole history. Each was stated in a commit, not inferred.

  1. 01

    Prose becomes a machine

    Every rule starts as a sentence in CLAUDE.md. If a machine can check it, it becomes a lint rule, a hook or a docs:check family, and the sentence is deleted. Seven project lint rules and more than thirty documentation checks are the residue.

  2. 02

    A rule that never fires looks clean

    A rule found dead four times in one day. A gate that passed only because the author's machine had no CRLF. Three docs:check rules that stayed green under sabotage. The answer is always the same: prove a new rule with a deliberate violation before trusting it, then search the tree by hand for the spellings of the violation its author did not think of.

  3. 03

    Gate the diff, read the report you have

    Mutation over changed files, e2e over reachable scenarios, one round of survivor-killing, and never re-running a gate to re-read its output.

  4. 04

    The author is the wrong reader

    The review is always an agent that did not write the diff. The pictures are read by an agent that does not know what they are for. The bot's lines are read as sentences with real values in them. The plan is criticised before code exists.

  5. 05

    A lesson left in the chat is gone

    The retrospective is a gate that falls before the release, not after it. Each lesson has to land as a rule, a check or a skill line. And since every file has a line budget, each new rule displaces an older one.

  6. 06

    Counts in prose rot

    A number that changes whenever a list changes is removed rather than corrected. The exception is a number something depends on: a check holds that one.
